### 4. IPC & Intercomputer Communication Topology Document

Created comprehensive architecture reference document **[docs/INTERPROCESS_COMMUNICATION_TOPOLOGY.md](file:///home/fekerr/src/irislime/docs/INTERPROCESS_COMMUNICATION_TOPOLOGY.md)**:

#### Summary of IPC / Network Methods Discussed:

1. **Local Disk Space File Mesh (Implemented)**:
   * **Mechanism**: Shared JSON files in `logs/nodes/` using atomic file replacement.
   * **Pros**: Cross-platform (Win11/WSL), zero external dependencies, human-auditable, persistent.
   * **Trade-Offs**: File I/O latency (~1–5ms); ideal for control-plane telemetry, node heartbeats, and task orchestration.

2. **Named Pipes (`\\.\pipe\` vs POSIX FIFOs `/tmp/pipe`)**:
   * **Mechanism**: Kernel-buffered stream pipes.
   * **Pros**: High throughput, sub-millisecond latency.
   * **Trade-Offs**: Windows Named Pipes and POSIX FIFOs use different APIs across the WSL2 hypervisor boundary.

3. **Loopback Network Sockets (`127.0.0.1` / Unix Domain Sockets)**:
   * **Mechanism**: Localhost TCP sockets or `/tmp/node.sock`.
   * **Pros**: Full-duplex streaming, microsecond latency, standardized client/server paradigms.
   * **Trade-Offs**: Requires port allocation management and bound listener lifecycles.

4. **Shared Memory (POSIX `shm_open` / Win32 `CreateFileMapping`)**:
   * **Mechanism**: Zero-copy RAM sharing.
   * **Pros**: Ultra-low latency (sub-microsecond).
   * **Trade-Offs**: Requires explicit mutex/semaphore synchronization; non-trivial across WSL2 VM memory space without Hyper-V socket bridges.

5. **Cross-Computer & Remote Node Communication**:
   * **HTTP REST & Server-Sent Events (SSE)**: Standardized for web UI & model load streaming (as used in `llama.cpp` `/models/sse`).
   * **gRPC / Protocol Buffers**: High-performance typed binary RPC for multi-machine compute clusters.
   * **Pub/Sub Brokers (MQTT / NATS)**: Scalable event-driven messaging across dynamic multi-node topologies.
   * **Cloud Storage Bus (`rclone` + Google Drive/S3)**: Asynchronous state synchronization across geographically separated machines.

### 2. Cross-Subsystem Rclone Delegation Feature

#### Architecture & Rationale
Because Google Drive OAuth tokens and `rclone` configurations reside natively on the Windows host (`%LOCALAPPDATA%\Microsoft\WinGet\Links\rclone.exe`), **WSL Ubuntu nodes delegate `rclone` operations to the active Win11 host node over the `mtfdash` mesh.**

```text
+-----------------------------------+       mtfdash mesh      +-------------------------------------+
|      WSL2 Ubuntu Guest Node       |  ====================>  |        Win11 Host Node (mtfdash)    |
| (Delegates: mtfdash-rclone-req)   |  logs/nodes/*.json      | (Executes: Windows rclone.exe)     |
+-----------------------------------+                         +-------------------------------------+
                                                                                 |
                                                                                 v
                                                                     +-----------------------+
                                                                     | Google Drive / Cloud  |
                                                                     +-----------------------+
```

#### Delegation Workflow & Commands
1. **WSL Node Issues Delegation Request**:
   ```bash
   python3 tools/mtfdash_node_manager.py rclone-delegate "copyto logs/archive.zip gdrive:transfer/archive.zip"
   ```
2. **Payload Injection**: Writes an `rclone:<operation>` command payload to the active `win11_host` node registry file in `logs/nodes/`.
3. **Host Servicing**: The Win11 `mtfdash` host node (running `get-mtfterminaldashboard.ps1` or `process-inbox`) intercepts the request, translates Linux POSIX paths via `wslpath -w` ([tools/wsl_rclone_bridge.py](file:///home/fekerr/src/irislime/tools/wsl_rclone_bridge.py)), executes Windows-native `rclone.exe`, and updates narrative receipts on the cluster ledger.
